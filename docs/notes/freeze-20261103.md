# Freeze 2026-11-03: the 08:30 boot stall was a `spu_context` ABI split

Date: 2026-11-03. Tree: `ps3recomp-play` (`exp/live-ab`), binary
`recomp-work/build-play`. Symptom: every boot after the 08:29 build showed
`[c690-stats] periodic ... jobs=3 in-flight=5` forever, the five `spurs pm`
lanes ended at `pc=0x108E8 lr=0x108E8 status=0x1`, and the FIFO later logged a
self-JUMP park (`0x207B1ED0` at `io=0x007B1ED0`) and a jump-park resync. The
start menu and match load never advanced.

**Cause: commit `decb3fb8` added `uint64_t src_seq` in the middle of
`spu_context`. The lifted SPU modules are compiled against a second copy of
`spu_context.h`, so every field after `resident_code` moved for the runtime but
not for the lifted code. The c690 job's command dispatch then read a stale
`dcache_id`/`host_depth`/`steps` and executed the invalid-command `stop 0x1` at
LS `0x1095C`.**

## 1. What was ruled out

| suspect | verdict |
|---|---|
| VFS writable files (HDDBlk, saves, caches) | **No.** No file under `recomp-work/vfs` changed between 07:40 and 08:36. The good `jobgap2` (08:05) and bad `jobgap3` (08:30) runs opened the **same six CACHE files** at the same relative times (47 s, 77 s, 103 s). The two VFS WADs and SDATs are byte-identical to the ISO copies (`cmp`). The 11-01 `.corrupt` files were a real but unrelated incident. |
| ISO mount | No: mounted, and all WAD/SDAT reads match the ISO. |
| `~/.cache` (Vulkan/ccache) | No runtime cache files changed in the window; the only `~/.cache` writes were ccache objects for the builds themselves. |
| `build-good` "stalls too" | **Not evidence.** `build-good` was configured with `SPU_DIR=ps3recomp-good/templates/project/spu`, which does not exist, so `build.ninja` contains **0** `spu_recomp.c` sources. It has no lifted SPU jobs at all; its wedge is a missing-SPU artifact, not the same failure. |
| the six `play_windowed.sh` speed switches | No: the stall is below them and reproduces with every switch off. |
| the 08:09 glibc crash | **Red herring.** That was the `SPURS_PM_FAST_RESCHED` double unlock (fixed in `07e90d16`); the B arm only. The regression starts with the 08:29/08:41 binary, not the 08:09 crash. |

## 2. Why the job stops at 0x1095C

Disassembly of the c690 module (EA `0x01161300`, base LS `0x4000`):

```
000108C4  23001307  brhnz  $r7, 0x1095C    ; opcode > 46 -> invalid command
000108E4  35201480  bisl   $r0, $r41       ; call handler[opcode]
000108E8            ^ return address
...
00010934  35800009  hbr    0x10958, $r0
0001095C  00000001  stop   0x1             ; abnormal stop
```

`pc=0x108E8, lr=0x108E8` on all five lanes is the link address of that dispatch
`bisl`; the job took the invalid-command `stop 0x1`. The 78 commands the
`[c690-stats]` histogram does show are all valid (0x00-0x2C), so the bad value
arrives from context state, not from a visibly bad opcode in the stream.

## 3. The ABI split

The generated lifted modules under `recomp-work/spu_lifted/<module>/` include

```c
#include "../../runtime/spu/spu_context.h"
```

which resolves through `recomp-work/runtime -> ps3recomp-native/runtime`
(created 2026-11-01). The runtime library is built from
`ps3recomp-play/runtime/spu/spu_context.h`. The two copies were compatible as
long as their shared prefix was identical.

`decb3fb8` (08:41, built 08:29) added:

```c
struct {
    uint32_t lsa, size, source_ea;
    int image_id, verify_state, source_index;
    uint64_t src_seq;          /* <-- inserted here */
} resident_code[4];
```

`resident_code` grows 96 -> 128 bytes, so `dcache_id`, `dcache_residency`,
`resident_task`, `host_depth`, `steps`, `module_img_a00`, the lockstep fields
and everything after it shift by 32 bytes in the runtime's view. The lifted
modules still used the old offsets. The runtime wrote the dispatch cache and
the drain step count at one address, the lifted dispatch read another: after a
few jobs the c690 dispatcher took the invalid-command path and stopped the
lane. The SPURS PM then ended inside the job (the `[pm-end]` lines), the
worker slots were never released (`in-flight=5`), and the GPU was starved --
the FIFO park/bad-word/resync lines are a downstream symptom, not the cause.

Offline proof with the two headers (same probe, same flags):

```
field                old lifted header   runtime before fix   runtime after fix
resident_code         265864              265864               265864
dcache_id             265960              265992               265960
host_depth            265972              266004               265972
steps                 265976              266008               265976
irq_gpr               266824              266856               266824
coh_listed            268880              268912               268880
sizeof                268896              268928               268928
```

## 4. Fix

Keep the O(1) memo, move its per-slot state to the **end** of `spu_context`:

* `ps3recomp-play/runtime/spu/spu_context.h`: `src_seq` removed from
  `resident_code[]`; new trailing field `uint64_t resident_code_src_seq[4];`
  with a comment that new fields must be appended, never inserted.
* `ps3recomp-play/runtime/spu/spu_channels.c`: the nine `src_seq` uses now read
  `ctx->resident_code_src_seq[slot]`.

All shared field offsets are then identical again; only `sizeof` differs
(268928 vs 268896), which is safe because the lifted modules never allocate a
`spu_context` and never touch the appended field.

Rebuilt `build-play`. Verified with three launches (see §6): the revert works,
the pre-fix HEAD stalls, the fix works.

## 5. Guard against recurrence

`recomp-work/ab-tools/check_spu_context_abi.sh` compiles one `offsetof` probe
against the build's `PS3RECOMP_DIR` header and one against the header the
lifted modules actually use (`recomp-work/runtime/spu`), then diffs every shared
field. New fields at the end are fine; a middle insertion fails with the exact
offset diff. It is called by `play_windowed.sh` (refuses to start) and by
`ab_live.sh` before the boot (exit 7). It skips builds whose `SPU_DIR` is not
the shared `recomp-work/spu_lifted`. `SPU_ABI_CHECK=0` overrides.

Regression test: the pre-fix header makes the probe fail with all offsets after
`resident_code` shifted by 32 bytes; the fixed header passes.

Offline tests after the fix: `run_code_dma_memo_test.sh` PASS (15/15),
`run_texdirty_range_test.sh` PASS (16/16), `test_spurs_scheduler.py` PASS,
`test_spurs_api_limits.py` PASS, `test_spurs_task_signal.py` PASS.

*after* the c690 stall, which is the same signature as the user's runs.
