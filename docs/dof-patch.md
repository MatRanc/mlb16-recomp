# Better depth of field: applying the EBOOT blur patch in the recomp

The close-ups and replays show doubled/outlined copies of the crowd and walls
(user screenshot, 2026-11-05). The game's depth-of-field pass is the last pass
of the frame: one RSX fragment program stored in the EBOOT, used by the 2X
MSAA and 4XR variants. RPCS3 gets a smooth blur from
[`MLB16_dof_fix.yml`](https://github.com/MatRanc/mlb16-revival-server/blob/main/patches/MLB16_dof_fix.yml),
generated by [`tools/dof_patch.py`](https://github.com/MatRanc/mlb16-revival-server/blob/main/tools/dof_patch.py).
This port loads the same EBOOT into guest memory and reads RSX fragment
programs from it, so the same bytes apply. Implemented on branch
`exp/dof-patch` (ps3recomp fork only).

## What the patch changes

- The original program is 0x340 bytes (two headers, 0x1121cc0 and 0x1122080,
  point at identical copies at +0x80).
- The replacement is 0xA90 bytes (168 16-byte slots through `PROGRAM_END`; 148
  real instructions, 20 inline-constant slots) and does not fit in the old
  space. It goes in the unused tail of the code segment's last 64 KB page,
  guest 0x10A4400. The EBOOT's first LOAD segment ends at 0x10A43E8 and the
  next starts at 0x10B0000, so 0x10A4400 is an ELF gap in the same page.
- Both headers get their size (0x0A90) and signed ucode offset
  (0x10A4400 - header) rewritten, plus the parameter tables. The game's own
  loader follows the headers, so the next `SET_SHADER_PROGRAM` names
  0x10A4400 instead of the old copy.

The blur is 16 taps on a golden-angle spiral plus the centre (2.4 px radius
at 720p, scaled by the pixel's blend factor). A tap is dropped when it is
nearer than the centre pixel and in focus, so a sharp ball cannot bleed into
the blurred crowd while a blurred player still spreads over what is behind
him. The sharp/blur blend is clamped to 0..1; the game's value reached ~2.4
for far objects. The depth/CoC part of the original is kept word for word.

## How it is applied in the runtime

New code: `ps3recomp/libs/video/rsx_dof_patch.{c,h}` and the generated table
`rsx_dof_patch_table.h` (generated by `tools/gen_dof_patch_table.py` from this
EBOOT and the user's `.yml`). `ppu_load_elf` calls `rsx_dof_patch_apply()`
right after the PT_LOAD segments are copied and before the guest entry point
runs.

- `PS3RECOMP_DOF_PATCH` (default `0`; `1`/`on` enables) is read at ELF load.
  It is not a live key: the bytes are applied once, and switching requires a
  relaunch.
- **Compatibility check first.** FNV-1a 64 fingerprints of the two original
  header+program regions (0x1121cc0 and 0x1122080, 0x3C0 bytes each) are in
  the generated table. If either does not match, or the 0xA90 target is not
  all-zero, or a header does not follow to 0x10A4400 after the write, the
  runtime refuses the patch, logs why, and runs the original program. It never
  writes into an unrecognised EBOOT.
- **The target is checked unused.** The runtime requires every one of the
  0xA90 bytes at 0x10A4400 to be zero before writing. The flat guest VM is
  zero-filled and the range is outside every PT_LOAD, which is the same tail
  the RPCS3 patch uses.
- **No stale cache.** The RSX backend keys compiled pipelines on the fragment
  code bytes/content hash, not on the guest address (rsx_d3d12_backend.c,
  `vp_get_fp_pso`), and the shader disk cache is keyed by the guest program
  identity plus translator version. Nothing reads or caches the fragment
  program at load time, so the first draw after boot sees only the patched
  bytes. The boot log has `[dof] applied Better depth of field at 0x010A4400
  (0xA90 bytes) to both program headers`; a refusal prints `[dof] refused:
  ...`.

## Offline proof

- `libs/video/tests/test_dof_patch.cpp` (built as `test_dof_patch` when
  glslang is present) reconstructs the generated program and runs it through
  the same decompiler the backend uses: **148 instructions decoded, no
  `unhandled FP opcode`**, and the emitted HLSL translates to SPIR-V for both
  export-control words (fp16 and fp32) and with texture gamma/sign-expand
  state on the three units it samples. All 25 checks pass.
- Given an EBOOT path, the same test loads the image, applies the patch and
  checks that both headers follow to 0x10A4400, that the bytes there are the
  generated program, and that a used target (`-2`) or a mismatched EBOOT
  (`-1`) is refused. With this EBOOT all pass.
- **No captured frame contains the DOF pass.** The `.fifo` captures were
  scanned for `SET_SHADER_PROGRAM` and the `.mem` images for the original
  0x340-byte program. The program bytes appear at guest 0x280 in
  `walker_replay.mem` and `logo_cap.mem`, but no draw references that address,
  and no captured local-memory page (where the game copies run-time programs)
  contains it. So there is no replay A/B for the DOF program itself; the
  decompile/compile and EBOOT-apply tests above are the offline proof.

## Live check (one pitch-meter launch)

`BUILD=build-dof PS3RECOMP_DOF_PATCH=1 ./recomp-work/ab-tools/ab_live.sh` with
A/A arms, 4 segments of 10 s at the pitch meter. The patch applied at boot
(`[dof] applied ...`), the meter was reached and X was pressed once. The first
four segments were 33.43 / 36.23 / 34.30 / 36.69 fps, in line with the same
meter on the A/A baseline (`ab_live_moire_aa_20261105_010818`, ~33-36 fps).
Segments 5-8 fell to 27.01 / 18.91 / 15.72 / 16.07 fps; the drop starts at
~01:16:05 and another mission relinked `recomp-work/build-play/MyGameRecomp`
at 01:16:12 during the measurement, so those numbers are contaminated by
external CPU/IO load, not attributable to the patch. The launch also
overlapped the last ~30 s of another mission's game during boot (its log ends
01:13:03), before the meter measurement started. Thumbnails stayed the normal
pitch view with no corruption. This checks no crash/hang with the key on; it
does not exercise the DOF pass itself (the meter view has none visible).

## User check: key off vs key on, ~3 minutes each

The key is an environment value applied at load, so this needs two short
launches (there is no live-ctl way to toggle it in a running session):

```sh
cd /home/m/Documents/mlb16-online/recomp-work
BUILD=build-dof PS3RECOMP_DOF_PATCH=0 ./play_windowed.sh   # baseline
BUILD=build-dof PS3RECOMP_DOF_PATCH=1 ./play_windowed.sh   # patched
```

In each launch, reach an instant replay or a walk-up / dugout close-up (the
shots with the `RECORDING` / `DEPTH OF FIELD` HUD are the ones). Look at the
background crowd and walls, and at the edge of a sharp player or the ball:

- key on: the background blur is smooth, with no doubled/outlined copies of
  the crowd and no halo around in-focus players; a sharp ball does not smear
  into the blurred background;
- key off: the doubled background / halo is the bug being fixed;
- both: no new corruption, and the boot log has `[dof] applied ...` for key
  on (a `[dof] refused ...` line means stop and report the EBOOT mismatch).

The pitch meter has no DOF pass, so its fps is only a regression guard.
